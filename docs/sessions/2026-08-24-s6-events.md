# 2026-08-24 — S6: event-log features, verified on real data

## What changed

`src/churnkit/features/events.py`, built test-first. 231 → 259 tests. Point-in-time
features from a long-format event log: rolling counts per window and event type,
window-over-window deltas and ratios, recency overall and per type, frequency
per active day, monetary sum and mean, engagement slope, longest inactivity gap,
and the month-on-month usage-drop flag. ADR 0007 has the design.

`assert_no_time_travel` runs **inside** `build_features`, not only in tests, as
S6 requires. `FeatureMatrix.source_dates` carries the latest contributing event
timestamp per row, which is what makes the I2 guarantee checkable rather than
merely claimed.

Also added a `clean` target to the Makefile, and removed 80MB of regenerable
caches. It deliberately leaves `mlruns/` alone — that holds the tracking
database and the registered model, so clearing it silently un-registers whatever
the API is serving.

## Verified on real data, not fixtures

Downloaded the UCI Online Retail dataset (541,910 transactions, 4,339 customers,
Dec 2010 – Dec 2011). It is an `.xlsx`, and rather than add `openpyxl` as a
dependency it was converted to CSV once with stdlib `zipfile` + `ElementTree` in
a scratch directory. No new dependency entered the project.

Three findings from putting the whole stack against it:

**1. The platform correctly refused to invent a target.** `infer_schema` reports
`target=None` with the warning that no column is binary and the churn definition
must be supplied. That is exactly right — this dataset has no churn column,
which is the case ROADMAP 2.2 exists for, and the honest answer was to say so.

**2. Event features are worth real accuracy.** Both figures below are temporal —
trained on features as of 2011-03-31, evaluated as of 2011-06-30:

| Feature set | AUC |
| --- | --- |
| Snapshot only (6 plain window counts) | 0.733 |
| Snapshot + event features (26) | **0.762** |

**+0.028 AUC from the event features**, which is S6's premise confirmed on real
data: accuracy comes from better features, not a bigger model.

**3. The random-split penalty depends entirely on drift, and here it was
small.** Temporal 0.762 against random 0.767 — an overstatement of only **+0.005**,
against **+0.238** on the synthetic drifting fixture in S5.

This is worth stating plainly rather than quietly omitting, because the S5
session note leads with the 0.238 figure. Retail purchasing behaviour between
these two quarters is stable, so pooling the periods and splitting at random
gives a model almost nothing it could not have learned temporally. The 0.238
figure is real but it is the *worst* case, not the typical one, and nothing in
this project should present it as what to expect. The honest claim is that a
random split is unbounded above: it costs nothing when the data is stable and
everything when it is not, and you cannot tell which case you are in without
doing the temporal split anyway.

Note the base rate itself drifted — 39.1% churn in the training period against
47.3% in the evaluation period — which is precisely the kind of shift a random
split would hide by averaging the two.

## A real bug the fixtures caught

The engagement slope was fitting across the full 90-day window, padding the time
before a customer's first event with zeros. That puts a leaving customer's
decline in the middle of a series that is flat on both sides, and a straight
line through that is horizontal — so a customer who fell from 15 events a month
to 3 scored as *steady*, with a slightly positive slope. It also penalised every
recent signup for not having existed for the whole window.

The fit now runs from the customer's earliest event in the window to the
prediction date. Verified by sign on three shapes: declining −0.021, growing
+0.017, steady −0.001.

## Known cost

Reading 541,910 rows through `read_table` takes ~57 seconds, and building
features for 3,035 customer-periods takes ~72 seconds. The parser is the larger
share and is non-streaming by design. Neither is addressed here; ADR 0007
records that `source_dates` is the correctness test any future vectorised
rewrite has to pass.

## Pick up next

**ROADMAP 2.2 — derive churn from an event log.** This session proved the gap is
real: on genuine transactional data the platform builds excellent features and
then has nothing to predict, because "churn" is not a column. The benchmark
above had to define it inline ("no purchase in the following 90 days"), and that
definition belongs in `churnkit` with the observation window, horizon and
censoring that `label_with_censoring` already implements.

Still open from S5: `reference/train.py` does not mark its metrics optimistic
despite having no time column (I1), so the PR-AUC 0.658 in `ROADMAP.md` is an
unmarked random-split number.
